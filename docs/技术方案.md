# TermPilot —— Agent 可操控的 SSH 终端工具 · 技术方案

> 修订（2026-09-24）：侧边栏不再做 SSH 端口转发（`-L/-R/-D`）和传输队列。
> 连接只有两种：正向 SSH（本机主动连服务器），反向监听（本机 `127.0.0.1` 等 shell 连入，公网暴露交给 cpolar 等外部穿透）。
> 侧边栏为「连接树 + 远程文件树」。下文若仍出现「端口转发 / 传输队列」字样，以本修订为准。

> 版本：v0.1（调研与选型阶段）
> 日期：2026-09-24
> 目标：开发一款类似 XShell 的桌面终端工具，既支持人工图形化操作（SSH 连接管理、SFTP 文件管理），又内置 MCP Server 让 AI Agent（Codex / Kimi Code 等）可以直接控制终端、读写服务器、截取屏幕（含滚动长截图拼图），并覆盖"无公网 IP 服务器通过内网穿透反弹回连"的场景。

---

## 1. 需求分析

| # | 场景 | 痛点 | 对应功能 |
|---|------|------|----------|
| 1 | 人工管理多台服务器 | 需要 XShell 式的会话管理、多标签终端 | 会话管理 + 多标签终端 |
| 2 | 上传/下载文件 | 需要图形化 SFTP | 双栏文件管理器（本地 ↔ 远程） |
| 3 | 服务器无公网 IP | 需要 frp / 反向 SSH 反弹回连本机 | 本地终端（node-pty）+ 端口转发管理 + 连接 `127.0.0.1:转发端口` |
| 4 | Agent 操作服务器 | Agent 无法直接驱动 GUI 终端 | 内置 MCP Server，暴露连接/执行/读写/截图等工具 |
| 5 | 比赛要求提交终端运行截图 | Agent 不好操作截图；数据量大时一屏截不下 | MCP 截图工具 + 滚动截图自动拼图 |
| 6 | GPU 算子开发 | 长编译/长测试输出需要完整留存 | 大 scrollback 缓冲 + 全文导出 + 长截图 |

## 2. 技术选型调研

### 2.1 框架：Electron + React 还是 Electron + Vue？

调研了 2026 年主流的开源终端/SSH 客户端实现：

| 项目 | 栈 | 说明 |
|------|-----|------|
| VS Code 终端 | Electron + xterm.js | 工业级事实标准 |
| Tabby | Electron + Angular + xterm.js | 知名 SSH 客户端 |
| electerm | Electron + React + xterm.js | 知名 SSH/SFTP 客户端 |
| Wave Terminal | Electron + React | 现代终端 |
| **tessera** | **Electron 33 + React 19 + electron-vite + xterm.js + ssh2 + node-pty + better-sqlite3** | 与本需求几乎完全同构的开源参考（SSH 会话管理 + 侧边栏 + 多标签） |
| Ferry | Electron + Vue 3 + electron-vite + xterm.js + ssh2 | Vue 系可参考的 SFTP/SSH 客户端 |

**结论：两者技术上都能做，xterm.js 本身与框架无关。但 React 做起来更快**，原因：

1. **参考实现更多、更贴近需求**：tessera 的架构（侧边栏会话列表 + 多标签 + SSH + safeStorage 存密码 + Zustand 状态）几乎是本项目的直接蓝本，大量设计决策（TerminalPool 单例、WebGL 渲染、IPC 通道划分）可以直接借鉴；electerm/Wave 也是 React。
2. **Agent/MCP 生态示例偏 React/TS**：electron-driver 等 MCP 驱动工具的示例与社区资料以 React 为主。
3. **xterm.js 集成难度相同**：Vue 和 React 都需要把 xterm 实例移出组件生命周期（见 4.2），没有本质差异。
4. Vue 的唯一优势是"如果开发者本人 Vue 更熟练"。若团队 Vue 经验远强于 React，可选 Vue 3 + Pinia，Ferry 可作为参考，其余设计不变。

**最终选型：Electron（最新稳定版）+ React 19 + TypeScript + electron-vite**

### 2.2 核心依赖清单

| 层 | 依赖 | 用途 | 备注 |
|----|------|------|------|
| 构建 | `electron-vite` + Vite | main/preload/renderer 统一构建，HMR | 目前 Electron 脚手架事实标准 |

## 3. 总体架构

```
┌──────────────────────────── Electron 主进程 (main) ────────────────────────────┐
│                                                                                │
│  SessionManager     SshConnectionPool      SftpService       TransferQueue     │
│  (会话CRUD/分组)    (ssh2 连接复用)        (ls/put/get/rm)   (上传下载队列)     │
│                                                                                │
│  PtyManager         ForwardManager         CaptureService    StorageService    │
│  (node-pty 本地)    (本地/远程/动态转发)   (截图/长截图)     (sqlite+safeStorage)│
│                                                                                │
│  ┌────────────────────────── McpServer (内置) ───────────────────────────┐    │
│  │  Streamable HTTP @ 127.0.0.1:<port>  +  Bearer Token 鉴权             │    │
│  │  tools: session.* / term.* / sftp.* / capture.* / forward.*           │    │
│  └───────────────────────────────────────────────────────────────────────┘    │
└───────────────────────────────────▲───────────────────────────────────────────┘
                                    │ 类型化 IPC（contextBridge 白名单 API）
┌───────────────────────────────────┴───────────────────────────────────────────┐
│                          渲染进程 (renderer, React)                            │
│                                                                                │
│  ┌──────────┐ ┌────────────────────────────────────────┐ ┌─────────────────┐  │
│  │ 侧边栏    │ │ 标签页区域                              │ │ SFTP 面板        │  │
│  │ (可收纳)  │ │ TerminalView × N (xterm.js + WebGL)    │ │ 本地栏 | 远程栏  │  │
│  │ 会话树    │ │ TerminalPool (单例, 重挂载不丢缓冲)     │ │ 传输队列         │  │
│  │ 转发管理  │ └────────────────────────────────────────┘ └─────────────────┘  │
│  └──────────┘ ┌────────────────────────────────────────┐                        │
│               │ 状态栏 (连接状态/延迟/转发端口)          │                        │
│               └────────────────────────────────────────┘                        │
└────────────────────────────────────────────────────────────────────────────────┘
```

**进程职责划分原则**：所有"能力"（SSH、PTY、SFTP、文件、截图、数据库）只存在于主进程；渲染进程只负责展示与交互，通过 preload 暴露的白名单 API 调用；MCP Server 与渲染进程**平级**，复用同一套主进程服务——Agent 和人是两个平等的"客户端"。

## 4. 核心模块设计

### 4.1 会话管理（XShell 风格侧边栏）

- 会话模型：`{ id, name, group, host, port, username, authType(password|key|agent), keyPath, jumpHostId?, encoding, envVars }`
- 侧边栏采用**标准收纳/展开（collapsible）形式**：
  - 分组树（文件夹可折叠，参考 XShell 的会话管理器）
  - 顶部搜索框过滤会话
  - 右键菜单：连接 / 复制会话 / 编辑 / 删除 / 新建分组
  - 侧边栏整体可折叠为窄图标栏（点击展开）
- 密码与私钥口令用 `safeStorage.encryptString` 加密后存 sqlite，绝不明文落盘。
- 会话支持"最近连接"排序与置顶。

### 4.2 终端模块（关键设计：TerminalPool 单例）

踩坑点（来自多个开源项目的共同教训）：**xterm 实例不能跟随 React 组件生命周期创建/销毁**，否则切换标签、折叠面板后终端缓冲丢失、TUI 程序不重绘就白屏。

设计：

- 每个会话对应**进程级唯一**的 `Terminal` 实例，挂在游离的 host `<div>` 上，订阅一次数据流；
- 标签页/分屏视图挂载时只做 **re-parent**（`el.appendChild(host)`），卸载时 detach，不销毁；
- 重新挂载后 `requestAnimationFrame` 内重新 `fit()` 并强制重绘一帧，避免空白；
- 渲染器：**WebGL addon 为默认且唯一默认**，监听 `onContextLoss` 自动重建（GPU 驱动崩溃/休眠恢复时）；Canvas 仅兜底；不引入 DOM renderer（等宽字体 fallback 会导致表格错位）；
- `FitAddon` + `ResizeObserver`：每次尺寸变化把 `cols/rows` 同步到 ssh2 的 `stream.setWindow()` 或 `pty.resize()`；
- scrollback 缓冲设大（如 50,000 行），为长截图和全文导出服务；
- 数据通道：主进程 ssh2 stream / node-pty ↔ IPC（`term:data:<id>` 推送，`term:input` / `term:resize` 上行）。大数据量用 `webContents.send` 分块 + xterm `write` 回调背压。

### 4.3 本地终端与内网穿透（反弹场景）

针对"服务器无公网 IP，反弹回连本机"：

1. **本地终端标签页**：基于 node-pty 的本地 PowerShell/WSL/bash 终端，可直接在本机跑 `frps`、`ssh -R` 服务端等；
2. **转发管理器（ForwardManager）**：
   - 支持三种转发：本地转发 `-L`、远程转发 `-R`、动态转发 `-D`（SOCKS5）；
   - 典型用法：目标服务器通过 frpc / `ssh -R` 把它的 22 端口反弹到本机 `127.0.0.1:60022` → 在本工具里新建一条指向 `127.0.0.1:60022` 的会话即可像普通服务器一样管理；
   - 侧边栏有独立的"端口转发"折叠分组，展示每条转发的状态（监听端口、目标、活跃连接数）；
3. 会话配置里允许把"经由转发"作为连接属性（先建立到跳板/回连点的 SSH，再 `forwardOut` 到内网目标），对 Agent 透明。

### 4.4 SFTP 文件管理

- 双栏布局（左本地、右远程），支持：
  - 目录浏览、排序、面包屑路径、新建/删除/重命名；
  - 拖拽上传/下载、多选；
  - **传输队列**：并发控制、进度条、失败重试、大文件分块（ssh2 `fastPut`/`fastGet` 或 sftp stream 自实现断点续传）；
- 与终端联动：终端面板可一键"同步当前远程目录"到 SFTP 面板（通过 shell 集成或 `pwd` 探测，MVP 阶段手动刷新即可）。

### 4.5 MCP Server（Agent 控制面）

内置 MCP Server，监听 `http://127.0.0.1:<port>/mcp`（Streamable HTTP），**强制 Bearer Token 鉴权**（Token 在设置页生成/复制，写入 Codex / Kimi Code 的 MCP 配置）。

工具集设计（v1）：

| 工具 | 说明 |
|------|------|
| `session_list` / `session_create` / `session_update` / `session_delete` | 列出、新建、修改、删除已保存连接。密码和私钥口令加密后入库，工具返回值不含明文 |
| `session_connect` / `session_disconnect` | 按名称或 ID 打开 / 断开终端。已打开的终端在改配置后不会自动重连 |
| `term_exec` | 在指定会话执行命令并等待输出（带超时与"静默期"判定，返回文本） |
| `term_write` | 向终端发送原始输入（含控制键，用于 TUI 交互） |
| `term_read` | 读取当前屏幕或最近 N 行 scrollback 文本 |
| `term_screenshot` | 截取指定会话终端当前可见区域（PNG，返回文件路径 + base64 可选） |
| `term_screenshot_scrollback` | **滚动长截图**：见 §4.6 |
| `sftp_list` / `sftp_mkdir` / `sftp_upload` / `sftp_download` / `sftp_rename` / `sftp_remove` | 文件管理。上传下载使用本机绝对路径；删除目录会递归 |
| `local_term_open` | 打开本机终端标签，之后用 `term_exec` 执行命令 |

设计要点：

- MCP 工具与 GUI 操作走**同一套主进程服务**，Agent 的连接在侧边栏可见、可被人接管，人的操作 Agent 也能通过 `term_read` 感知——这是相对"Agent 自己起 ssh 进程"的核心优势；
- 危险操作（`rm`、写系统路径等）可选"需人工确认"模式：MCP 调用触发 GUI 弹窗，人点确认后才执行；
- 所有 MCP 调用写审计日志（sqlite），方便比赛材料追溯。

### 4.6 截图与滚动长截图拼图

**普通截图**：主进程 `webContents.capturePage(rect)` 截取终端区域，或前端把 xterm 可见区渲染到离屏 canvas。返回 PNG。

**滚动长截图**（核心难点，两种方案对比）：

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| A. 滚动拼接 | 逐屏滚动 xterm → 每屏 capturePage → 按重叠行对齐拼接 | 实现直观 | xterm 是虚拟滚动+WebGL canvas，滚动动画/重绘时序导致拼接错位、重复行；需要复杂的对齐算法 |
| **B. 缓冲重渲染（推荐）** | 从 xterm `buffer.active` 直接读取指定行范围（含 scrollback），用**等宽单元格**把每行文本+颜色属性绘制到离屏 Canvas（每字符一格，行列对齐天然精确），一次性输出完整长图 | 无滚动、无时序问题、无拼接误差；可精确指定行范围；速度极快 | 需自实现 cell→canvas 绘制（约 200 行代码，含前景/背景/粗体/下划线） |

**选择方案 B 为主**：`term_screenshot_scrollback({ sessionId, startLine?, endLine? })` → 主进程从渲染进程取回 buffer 序列化数据（行文本 + 属性）→ 离屏 canvas 逐行绘制 → 输出 PNG（超长时按高度切片输出多文件，如 `shot_001.png, shot_002.png`，避免单图超过 PNG 尺寸限制）。

方案 A 作为兜底保留（当需要截取包含非终端 UI 元素的完整窗口时）。

### 4.7 安全模型

- `contextIsolation: true`、`sandbox: true`、`nodeIntegration: false`；
- preload 只暴露类型化白名单 API（`window.api.*`），不暴露 `ipcRenderer` 本体；
- MCP Server 只绑定 `127.0.0.1`，必须 Token 鉴权；
- 凭据一律 `safeStorage` 加密；
- 不加载远程内容，CSP 收紧。

| M4 穿透 | ForwardManager（L/R/D）+ 侧边栏转发面板 | 反弹回连全流程打通 |
| M5 MCP | 内置 MCP Server + 核心工具（session/term/sftp） | Agent 可连接执行命令 |
| M6 截图 | 普通截图 + buffer 重渲染长截图 + 切片导出 | Agent 可提交比赛截图 |
| M7 打磨 | 审计日志、危险确认、主题、打包 NSIS | 可发布版本 |

## 8. 风险与对策

| 风险 | 说明 | 对策 |
|------|------|------|
| **node-pty Windows 构建** | 最大已知坑：winpty/conpty 编译需 Python + VS C++ 工具链，且必须按 Electron ABI 重编译 | 使用 `electron-rebuild`；vite 配置 `external: ['node-pty']`；CI 预编译；实在不行可降级用 `ssh2` 只连远程 + 本地用 conpty 的预编译 fork（如 `node-pty-prebuilt` 类方案） |
| WebGL 上下文丢失 | GPU 驱动崩溃/休眠后 canvas 黑屏 | 监听 `onContextLoss`，dispose 后重建 addon |
| 长截图内存 | 5 万行 buffer 重渲染图片巨大 | 按行范围截取 + 自动切片输出多文件 |
| ssh2 大数据吞吐 | 大文件传输/刷屏时 IPC 压力 | 分块发送 + xterm write 回调背压；SFTP 走独立通道不占终端流 |
| MCP 安全 | Agent 获得服务器完整控制权 | Token 鉴权 + 仅回环监听 + 危险命令人工确认模式 + 审计日志 |
| SQLite | 使用 Electron 自带的 `node:sqlite`，不引入 `better-sqlite3` | 避免再做一次原生 ABI 重编译 |
